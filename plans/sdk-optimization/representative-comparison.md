# 최종 버전과 기존 버전의 실제 API 비교

상태: 측정·검산·문서 반영과 최종 통합 리뷰 완료. 전체 Graph·Cloudflare는 제외한다. 기존 workstream 완료와 별개인
후속 실측이며, 이전의 부분 최적화 실험을 최종 버전의 성능으로 대체하지 않는다.

확인된 주요 이득은 Go의 파일 수·무변경 캐시 빌드 비용 감소와 GitHub TS의 전체 strict
타입 검사 시간 감소다. 생성 시간·Go cold 시간·cold 최대 RSS의 전반적인 개선은
입증하지 못했다. 작은 TS 출력과 일부 생성/검사 시간은 증가했다.

## 고정한 비교 조건

- 기존 제품은 `5ada624a69ebfd85103248379970f78a8f3d2899`, 최종 제품은
  `52eab9882d4a4df33b0131b119f37d87c254344b`다. 두 revision의 실제 `cmd`·`internal`·
  `go.mod`·`go.sum`을 archive로 추출하고 같은 도구·빌드 옵션으로 각각 빌드한다.
- TVMaze(42개 API), ListenNotes(24개 API), GitHub(1,221개 API)의 고정 실제 원본을
  사용한다. 작은 두 문서와 더 큰 문서의 사례 비교이며 전체 제공자의 통계 표본은 아니다.
  입력 경로와 SHA-256은 `compare-apis.py`에서 검증하며 선택 옵션 없이 server를 포함한다.
- Go 1.27.2, Node 24.22.0, TypeScript 5.9.3, CGO=0, Go `GOMAXPROCS=4`,
  Go `-p=1 -trimpath -buildvcs=false`, Go soft heap 4 GiB, Node heap 5 GiB를 사용한다.
  phase별 600초·관측 session RSS 6 GiB, 전체 7,200초를 상한으로 한다.
- 각 입력·대상에서 기존/최종 순서를 바꾸며 5쌍을 직렬 실행한다. 모든 생성은 새 출력이다.
  생성기 빌드·입력 및 설정 준비는 생성/컴파일 시간에서 제외한다. 첫 표본도 보존한다.
- Go cold는 매번 빈 전용 `GOCACHE`에서 표준 라이브러리를 포함해 전체 `./api/...`를
  빌드한다. warm은 바로 그 출력·캐시에서 수정 없이 같은 명령을 다시 실행한다.
- TS cold는 build-info 없이 전체 strict source와 기존 SDK에서 동결한 공개 계약을 검사한다.
  warm은 같은 build-info를 재사용하는 무변경 증분 검사다. 둘 다 새 Node 프로세스다.
  기존 canonical 설정의 `noEmit` 타입 검사이며 JS·선언 파일 방출 시간은 포함하지 않는다.
  Go의 compiler cache와 TS의 증분 검사 cache는 서로 다른 경계다.
- OS·파일시스템 cache는 비우지 않는다. warm은 수정된 package를 다시 컴파일하는
  증분 개발 시간이나 원격 HTTP 응답 시간을 측정하지 않는다.
- 시간은 fresh worker의 subprocess wall time으로 측정한다. Linux wait4 계열의
  RSS high-water는 가장 큰 개별 자식/후손 프로세스의 최대치다. 동시 전체 메모리가 아니다.
  별도로 200ms 간격의 session RSS 합을 기록하며 공유 페이지 중복과 짧은 peak 누락이 있다.
- 알려진 실패를 반복하지 않는다. 첫 실패 쌍을 보존하고 해당 입력·대상의 나머지 쌍은
  중단한다. 실패·timeout·RSS 종료를 성공 표본이나 개선율 계산에 넣지 않는다.

## 문서 반영 범위

현재 공개 문서는 소스 감소를 고정 속도 향상으로 해석하지 말라고 설명하고 있다.
캐시의 정확한 경계, 출력 파일 묶기의 변경 비용, TypeScript 공유의 효과 범위는 보완한다.
공개 숫자는 GitHub Actions 실행에 연결한다는 프로젝트 규칙을 유지한다. 이번 로컬
실측과 원시 자료는 내부 개발 기록에 보존하고 공개 benchmark처럼 게시하지 않는다.

## 리뷰와 완료 조건

1. 하네스: revision/input/tool pin, 동등한 옵션, cache 격리, 시간·RSS 경계, 실패 분모를 검토한다.
2. 실측: 양쪽 생성과 전체 컴파일 성공, 출력 manifest hash, 원시 표본과 집계를 대조한다.
   성공한 작은 입력만 전체 개선으로 확대하지 않는다. 모든 실패와 미측정 범위를 기록한다.
3. 문서: 영어·한국어 TS/Go 비용 페이지의 기존 주장을 확인하고 사용자가 선택할 조건과
   손해를 명시한다. 문서 검증·빌드를 수행한다.
4. 각 작업 단위 리뷰와 커밋 뒤 최종 통합 리뷰에서 코드·결과·문서의 일치를 확인한다.

하네스 리뷰에서는 이전의 200ms 외부 recorder 시간을 짧은 작업의 실행 시간으로 쓰지
않도록 fresh worker의 내부 시간을 추가했다. memory high-water와 session RSS 합도
별도 필드로 구분했다. 실패·비대응 쌍 제외와 실제 실패 종료 코드·메모리 측정 검사2개,
기존 recorder 검사5개가 통과했다. TVMaze 예비 실행의 양쪽 TS/Go 생성·cold/warm도
모두 통과했다. 예비 실행은 도구 검증에만 쓰며 성능 집계에 섞지 않는다. 최초 sandbox의
전역 Go cache 쓰기 실패도 별도 기록으로 남겼고 이후 정상 cache 접근으로 재실행했다.

## 드라이버 중단과 표본 보존

최초 호스트 실행은171개 성공 명령 이후, GitHub Go의3번 쌍 최종 버전 warm이 끝나고
기존 버전을 시작하기 전에143으로 종료됐다. 원인은 확인되지 않았으며 최초 외부 recorder의
최종 `result.json`은 없다. 살아 있는 원래 controller가 없음을 확인했다. 완료된 측정의
실패나 timeout으로 재분류하지 않으며, 한 번의 외부 실행 전체가 통과했다고도 주장하지 않는다.

`resume-apis.py`는 기존171개 원시 표본·상태의 snapshot을 먼저 보존하고, 빠진 Go
전체 사례3개만 계획된 순서대로 실행한다. 부분 사례를 덮어쓰거나 warm 캐시를 cold로
재사용하지 않는다. 기존 worker·recorder·입력·생성기 binary hash를 확인하며 실제 측정은
변경하지 않은 `compare-apis.py _child`가 수행한다. 새 driver의 hash와 환경을 별도 기록한다.
중단 경계를 걸친3번 쌍의 시간 간격과 시스템 swap 관측은 해석의 한계로 유지한다.

## 실제 이득과 손해

비용 변화율은 `(최종 중앙값 / 기존 중앙값 - 1) × 100`이다. 아래의 paired 비율은
각 쌍의 최종/기존 시간 비율의 기하평균이며, 가능한 5^5개 재표집의 percentile 95% 구간을
사용한다. 중앙값 변화율과 서로 다른 통계량이다. 작은 표본과 환경 변동을 제품 전체의
속도 보장으로 확대하지 않는다.

- Go 파일 수는 TVMaze 74.78%, ListenNotes 80.18%, GitHub 77.28% 줄었다.
  관리 파일 바이트 감소는 각각 2.43%, 2.04%, 2.57%다. 파일 수 감소율을 소스 크기나
  컴파일 시간 감소율로 바꾸어 해석할 수 없다.
- Go 무변경 warm 명령 시간 중앙값은 각각 22.30%, 36.79%, 55.44% 줄었다.
  paired 비율의 95% 구간도 각각 [0.7539, 0.7857], [0.5587, 0.6353],
  [0.2772, 0.7290]으로 이 표본에서는 모두 감소 방향이다. 이는 실제 재컴파일이 아닌
  캐시를 확인하고 재사용하는 명령 비용이다. GitHub warm의 최대 RSS 중앙값도 49.06% 줄었다.
- Go cold 시간 중앙값 변화는 +0.10%, -0.66%, +0.37%이며 세 paired 구간은 모두1을
  포함한다. 뚜렷한 cold 개선을 입증하지 못했다. GitHub의 기존 범위는196.90–218.43초,
  최종 범위는196.27–256.98초다. 최종의 긴 실행도 제외하지 않았다.
- GitHub TS 전체 strict 타입 검사 중앙값은10.82% 줄었다. paired 비율0.9079의
  95% 구간은[0.8660, 0.9549]다. 반면 cold 최대 RSS 중앙값은1.25% 늘었다.
  warm 시간 중앙값은2.85% 감소했지만 구간[0.8043, 1.0588]이1을 포함해 뚜렷한
  warm 개선으로 결론 내리지 않는다. 출력은3.13% 작아졌지만 파일은25개 늘었다.
- 작은 TS 출력은 TVMaze 1.62%, ListenNotes 1.05% 늘었다. TVMaze 생성은
  0.1316→0.1355초로2.90% 증가했고 paired 구간도 증가 방향이다. ListenNotes warm
  검사는0.5155→0.5258초로1.99% 증가했다. 절대 차이는 각각 약4ms·10ms다.
  작은 입력에서 시간·크기·메모리가 모두 좋아졌다고 안내하지 않는다.
- 생성 시간의 일관된 이득은 없다. ListenNotes Go는2.72% 증가했으며 paired 구간도
  증가 방향이다. GitHub Go는 중앙값상0.62% 감소했지만 paired 비율1.0005의
  구간[0.9740, 1.0237]은1을 포함한다. 생성 최대 RSS도 GitHub Go는1.58% 늘었다.
  작은 메모리 차이는 개별 실행의 범위와 함께 읽으며 전반적 메모리 개선을 주장하지 않는다.

## 확인하지 않은 범위와 해석 조건

이번 비교는 같은 입력·도구·옵션·heap 정책·실행 순서를 고정한 한 WSL 환경의 직렬
측정이다. OS 파일 캐시·CPU 스케줄·시스템 전체 swap은 완전히 격리하지 못했다.
GitHub Go cold 구간에서 전역 swap counter 증가를 관측했다. 한 시점의 Go/compile
`VmSwap=0` 진단도 남겼지만 전체 기간의 swap 귀속이나 시간 차이의 원인을 입증하지는 않는다.
Go soft heap 4 GiB 조건의 결과이며 무제한 heap에서의 시간·최대 메모리 수요로 일반화하지 않는다.

API 수정 후의 증분 재컴파일, JS·선언 파일 방출, 실행 파일·압축 배포물 크기, 원격 HTTP
지연·호출별 할당, 다른 Go/TS compiler·다른 플랫폼의 성능은 새로 측정하지 않았다.
전체 Graph·Cloudflare도 실행하지 않았다. 출력 계약 대조는 컴파일/표현 계약의 근거이며
모든 API를 실제 제공자 서버에 호출한 근거가 아니다. 각 최적화의 개별 기여도도 분리하지 않았다.

## 원본 검산과 문서 확인

`verify-representative-comparison.py`는180개 고유 명령과 실제 metrics/recorder/log의
일치, 고정 입력·archive/binary·실제 추출 source의 동일성을 확인했다. 기존171개 표본은
복구 snapshot과 정확히 같다. 12개 입력·대상·버전 조합의 각5회 관리 출력 hash가 모두 같다.
Go 세 입력은 전체 audit에서 기존 계약 차이0개·사전 검토한 내부 추가8개만 확인했다.
추가 계약은 기존 canonical 문서의 import root만 미리 정한 값으로 바꾼 파생 자료이며,
발견한 차이에서 예외를 만들어내지 않았다.

복구 경계를 걸친3번 쌍을 제외한 보조4쌍 분석에서도 GitHub Go의 생성/cold 개선은
불확정이고 warm 감소 방향은 유지됐다. primary 결과는5쌍 전부를 유지한다.
실제 producer·원본 입력·모든 phase 기록·소비 검사 설정·managed manifest·Go audit·
복구 snapshot·진단과 index를 `measurements/2026-10-22/representative-final-comparison.tar.gz`에
보존했다. 65,558,818 B·1,727 entry, SHA-256은
`ba0e79a365b4ee3a5253eeacaeb77be417c8263f174378658dd0af995c4eb30c`다.
모든 index 항목의 크기·hash를 archive에서 다시 읽어 검산했다. 실행 파일·compiler cache·
build-info·전체 생성 SDK는 제외하며, source는 고정 Git revision과 입력으로 재생성한다.

영어·한국어의 TS/Go 비용4페이지·호환성4페이지·문제 해결4페이지를 확인했다.
