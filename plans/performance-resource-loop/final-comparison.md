# 지속 최적화 작업 전후 비교

2026-10-23 사용자 요청으로 추가 최적화를 종료했다. 시작점은 `v1.4.0`의
`6231d70`이고 유지한 제품 runtime은 `5b9312d`다. 그 뒤 추가된 진단 도구와
종료 기록은 제품 생성 동작을 바꾸지 않는다. 최종 압축 후보는 성능 손해로 기각했다.

## 시작 시와 최종 상태의 관측

다음은 고정 GitHub 실제 API의 로컬 CLI 기록이다. **최종 상태와 시작 버전을 같은
시점·동일 조건으로 다시 번갈아 측정한 결과는 아니다.** 시작 자료는 5회, 최종 자료는
3회다. Go 1.27.2·server addon·GOMAXPROCS=4·GOMEMLIMIT=2GiB는 같지만 측정 시점과
import root(`example.test/matched/api` → `example.test/graph/api`)가 다르다.
종료 요청에 따라 새 비교 실행은 추가하지 않았다. 아래 변화율은 기록 간 참고치다.

| 지표 | 시작 시 기록 | 유지한 최종 상태 기록 | 해석 |
| --- | ---: | ---: | --- |
| 생성 시간 중앙값 | 56.0083초 | 35.5619초 | 약 36.5% 짧게 관측. 최종 통제 비교의 확정 개선율은 아님 |
| user+system CPU 중앙값 | 62.8727초 | 39.9784초 | 약 36.4% 적게 관측 |
| 최대 process RSS 중앙값 | 600.28 MiB | 608.90 MiB | 약 1.44% 증가. 최대 메모리 절감은 입증하지 못함 |
| 출력 크기 | 203,264,540 B | 204,611,637 B | 약 0.66% 증가. 공개 문서 주석 복원과 import root 차이를 포함 |
| 파일 수 | 6,375개 | 6,377개 | 주석 복원 후 묶음 결과 변경. 공개 API/실행 계약 검증 유지 |
| 생성 SDK cold/warm 컴파일 비용 | 이번 작업의 최종 비교 없음 | 재측정 안 함 | 컴파일 시간·컴파일 메모리의 개선을 주장할 근거 없음 |

생성 시간 범위는 시작 55.2764–57.3755초, 최종 35.5276–35.9171초다.
RSS는 개별 실행의 Linux `RUSAGE_CHILDREN` high-water다. OS 전체/WSL 점유량이나
누적 할당이 아니다. 여러 작업 단위의 백분율을 더하거나 곱해 누적 개선율을 만들지 않았다.

원시 값과 계산은 [기계 판독 비교 자료](measurements/final-comparison.json)에 있다.
시작 표본은 [01 근거](measurements/01-partition-format.tar.gz)의 `comparison/trials.json`,
최종 유지 제품의 3회 표본은 [14 근거](measurements/14-partition-source-storage.tar.gz)의
`unit14/cli-verification.json`에서 `baseline`인 행이다. 이 archive의 `candidate`는 기각된
압축 후보이므로 최종 제품 수치에 사용하지 않는다.

## 동일 조건에서 확인한 개선

각 수치는 해당 작업 직전 버전과 비교한 결과다. 서로 다른 측정 범위를 구분한다.

| 변경 | 직접 확인한 효과 | 범위 |
| --- | --- | --- |
| 중복 AST 포맷 제거 | GitHub 생성 시간 −13.83%, CPU −13.81% | 실제 CLI, 같은 조건 5쌍 |
| 분할 참조 분석의 중복 파싱 제거 | 누적 할당 −6.44% | 동일 관측기 3쌍 |
| facade 원본/AST 소유권 정리 | 시간 −10.66%, 할당 −9.54%; 누락된 주석 복원 | 해당 단계 관측기 비교, RSS +0.75% 비용 보존 |
| emission 템플릿 파싱 공유 | 시간 −4.00%, 할당 −6.55% | 해당 단계 관측기 비교, RSS +1.32% 비용 보존 |
| AST 자식 필드 구조 재사용 | 시간 −2.06%, CPU −1.82% | 해당 단계 관측기 비교, RSS +1.06% 비용 보존 |
| 최종 serialization scratch 재사용 | 누적 할당 19.51→18.62 GB, −4.55% | 직전 제품 대비 관측기 3쌍. 최대 RSS 절감으로 해석하지 않음 |

전체 변경과 실패/기각 근거는 [작업 기록](../performance-resource-loop.md)의 단위별 문서와
archive에서 확인할 수 있다. 관측기에는 준비 후 강제 GC와 파일 hash 기록이 들어가므로
관측기 시간/메모리를 실제 CLI 비용으로 대체하지 않는다.

## 작은 API와 검증 한계

TVMaze는 143개·3,172,460 B, ListenNotes는 201개·7,546,903 B를 유지한다.
최종 유지 CLI의 단발 정확성 실행은 각각 0.2598초/48.00 MiB,
0.4817초/56.50 MiB였다. 단발 실행으로 작은 API의 개선율을 주장하지 않는다.
이 수치는 [12 근거](measurements/12-identifier-rewrites.tar.gz)의 실제 CLI 검증에서 가져왔다.

최종 제품의 세 실제 API 전체 파일 hash·소비자·주석·이름 바인딩·초기화/독립성·
오류·게시 소유권·관련 race 검증을 완료했다. 마지막 후보에서도 관련 31개 검사와
실제 API 전체 출력은 통과했으나 비용이 나빠져 채택하지 않았다.
전체 Graph/Cloudflare, 전체 compiler/platform matrix, TypeScript의 추가 성능 비교는
이번 지속 최적화 범위에 다시 넣지 않았다. 로컬 수치는 공개 benchmark 문서에 게시하지 않았다.

## 기각한 마지막 후보와 자원 정리

같은 조건의 실제 CLI 3쌍에서 압축 보관 후보는 시간 중앙값 35.5619→39.5344초
(+11.17%), CPU 39.9784→45.0068초(+12.58%), 최대 RSS 608.90→562.52 MiB(−7.62%)였다.
보유 heap 감소만으로 채택하지 않고 유지 제품으로 복구했다.

측정 도구는 작업별 cache 격리, cold/warm pair cache 회수, 취소 시 하위 프로세스 회수를
개선했다. 이는 생성 SDK의 컴파일 속도 향상과 다른 효과다. 작업 중 전용 cache는
4 GiB, cache 외 생성물/임시 파일은 2 GiB 운영 한도 안에서 관리했다.
종료 정리에서 작업 전용 cache와 임시 생성물/실행 파일을 담은
`.tmp/perf-resource-loop/` 전체를 삭제했다. 삭제 전 할당량은 4,053,913,600 B
(약 3.78 GiB), 그중 전용 Go cache는 약 3.39 GiB였다. 전역/다른 작업의 cache는 정리 대상에
포함하지 않았다. 추가 빌드나 성능 측정은 실행하지 않았다.

15개 근거 archive의 2,916개 항목을 길이·SHA-256으로 검산한 뒤 정리했으며,
archive 약 46.94 MiB와 비교/종료 문서를 보존한다.
[정리 결과와 보존 자료 hash](measurements/final-cleanup.json)에 범위를 기록했다.
