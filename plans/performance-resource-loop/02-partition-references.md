# Go 분할 참조 분석의 중복 파싱 제거

상태: 구현·실측·전체 출력 대조·관련 검사·최종 리뷰 완료. 채택한다.

## 근거와 설계

기준 제품은 첫 개선을 적용한 `28c523d`다. 이전과 같은 GitHub 원본과 server
addon을 사용하는 진단 도구에 단계별 `runtime.MemStats.TotalAlloc`과 선택적 heap
profile을 추가했다. 이 도구의 수치는 CLI의 순수 생성 시간과 구분한다.

기준 진단 실행에서 완료 시점 누적 할당은 27,407,705,864 B였다. sampled
`alloc_space` profile에서 `partitionPackageBound` 첫 파싱에 약 1.71 GiB,
두 번째 파싱에 약 1.73 GiB가 귀속됐다. 누적 할당은 peak RSS나 동시에 살아 있는
heap 크기가 아니며, 이 값을 메모리 점유량으로 안내하지 않는다.

분할기는 모든 파일의 선언을 먼저 알아야 파일 간 의존성을 연결할 수 있다.
기존 구현은 선언 색인 후 같은 파일을 다시 파싱하여 참조를 찾았다. 후보는 첫 AST가
살아 있을 때 package-level 참조 이름만 추출한다. 선언 색인이 끝나면 이 이름을
기존 심볼 표에 연결한다. AST를 캐시하지 않고 각 파일의 참조 목록도 연결 즉시 해제한다.
지역 변수·선언·필드·selector 처리 규칙, DAG/SCC 배치, 비공개 심볼 이름과 공개 facade는
기존 규칙을 유지한다. 제공자별 분기나 전역 cache는 추가하지 않는다.

전방 참조·재귀 타입·지역 변수 이름 가림을 한 생성 소비자에서 함께 검사하는 사례를
추가했다. 검사 코드를 추가하는 과정의 raw string 내부 삽입 오류는 수정했고 최초 실패를
보존했다. 기존 `TestPartition*`와 새 검사는 `CGO_ENABLED=1`의 race 소비자 실행까지
통과했다.

## 동일 조건의 관측 결과

같은 observer 소스를 기준·후보 제품과 각각 빌드했다. GitHub는 순서를 바꾼
3쌍, TVMaze·ListenNotes는 정확성 확인용 각 1쌍이다. CPU·heap profiling을 끄고
실행했고, 각 observer의 컴파일·준비·입력 해제 GC·생성·출력 hash·게시 비용을 포함한다.
순수 CLI나 생성 SDK 컴파일 시간 측정이 아니다. Go 1.27.2, `-trimpath`, `GOFLAGS=-p=2`,
`GOMAXPROCS=4`, `GOMEMLIMIT=2GiB`, session RSS 보호 3 GiB, 개별 180초 조건이다.
각 실행은 새 프로세스와 새 출력이며 모든 파일을 검산한 후 출력을 제거했다.

아래는 GitHub 각 3회 중앙값이다. 시간은 기존 subprocess worker, 할당은 observer의
게시 완료 checkpoint, RSS는 Linux `RUSAGE_CHILDREN`의 최대 개별 프로세스 high-water다.

| 지표 | 기준 | 후보 | 중앙값 변화 |
| --- | ---: | ---: | ---: |
| 실행 시간 | 47.0335초 | 45.6263초 | -2.99% |
| user+system CPU | 52.9193초 | 51.3732초 | -2.92% |
| 누적 할당 | 27,406,821,488 B | 25,642,844,544 B | -6.44% |
| 최대 RSS | 612.96 MiB | 604.69 MiB | -1.35% |

누적 할당은 실행 중 생겼다가 해제된 할당을 모두 합친 값이다. 동시에 27 GB를
점유했다는 뜻이 아니다. 기준 범위는 27,406,112,568–27,407,175,088 B, 후보는
25,642,820,192–25,643,490,840 B다. 3쌍에서 반복된 약 1.76 GB의 할당 감소가
채택의 주 근거다. 실행 시간 범위는 기준 46.52–47.18초, 후보 45.04–46.67초다.

RSS 범위는 기준 609.39–616.04 MiB, 후보 603.95–613.74 MiB로 겹친다.
두 번째 쌍에서는 RSS가 소폭 증가했다. 작은 표본의 중앙값 감소를 일관된 peak
메모리 개선이나 다른 입력에서의 메모리 보장으로 확대하지 않는다.

GitHub 출력 6,377개, 203,199,878 B는 모든 실행에서 기존 파일별 hash와 같았다.
작은 입력도 전체 출력이 같았다. TVMaze 143개·3,172,460 B, ListenNotes
201개·7,546,903 B다. 작은 입력의 표본은 성능 결론용이 아니며, 해당 경로의
뚜렷한 할당·시간 절감을 주장하지 않는다. import root는 `example.test/graph/api`다.
앞 단위의 CLI·import root 조건과 다르므로 시간·바이트를 직접 합산하거나 교차 비교하지 않는다.

## 검증과 리뷰

| 영역 | 완료 근거 |
| --- | --- |
| 선언과 참조 분석 | 첫 AST에서 이름만 추출하고 전체 선언 색인 후 연결한다. 동일 파일·미정의 이름 제외, 사용자 목록과 정렬된 의존성 집합은 기존 의미를 유지한다. |
| 수명·자원 | 전체 AST를 유지하지 않는다. 참조 이름 목록은 연결 후 해제한다. 전역 cache·제공자별 분기를 추가하지 않았다. |
| 심볼·순환·지역 이름 | 기존 `TestPartition*` 4개와 새 전방 참조·순환 타입·이름 가림 검사 통과. 생성 소비자는 race 검사까지 실행했다. |
| 묶기·공개 계약·게시 | 최종 제품에서 기존 `TestPack*` 통과. 새 공개 계약·파일 배치를 추가하지 않았다. |
| 관측 도구 | 양쪽 observer 소스 hash가 같다. 누적 할당과 live heap을 구분하고, heap 수집은 선택적이며 게시 완료 후 수행한다. README에 범위를 명시했다. |
| 실제 출력·증거 | 고유 표본 10개, 바이너리·입력·생산 스크립트·로그·source manifest·checkpoint·출력 inventory를 별도 검산했다. 관련 제품 변경은 Go 분할 구현과 그 검사다. |

측정한 제품 소스와 이 단위의 최종 소스가 같다. 전체 compiler/TypeScript 매트릭스나
37개 Go corpus의 컴파일을 반복하지 않았으며, 해당 전체 검사를 새로 통과했다고 주장하지 않는다.
원래와 byte 단위로 같은 실제 출력, 관련 소비자·게시 검사, 분석 단계의 의미 보존을 확인했다.
현재 검토 범위의 미해결 결함은 없다.

## 보존과 한계

[원시 근거](measurements/02-partition-references.tar.gz)는 1,413,608 B다.
근거 항목 176개와 색인 1개를 포함하며 동일 내용은 tar hard link로 중복 저장하지 않는다.
`evidence-index.json`의 모든 항목을 다시 읽어 크기와 hash를 확인했다.
SHA-256: `5aa25c5c6fe2868a03b35fca1b2d643a0fbfb171ec8eefcdbb65d1cc9cc73672`.
진단 CPU·heap profile, checkpoint, 예비 결과, 관련 검사 실패·재검증,
10개 실측과 출력 inventory, 검산·생산 스크립트와 관련 소스를 포함한다.
SDK 출력·실행 파일·Go cache는 포함하지 않는다.

전용 Go cache는 검사 후 약 2.1 GiB, Go 임시 디렉터리는 비어 있었다.
기존 4 GiB cache·2 GiB 생성물 상한과 직렬 실행을 유지했다. 공용 Go cache는 쓰지 않았다.
파일 cache·다른 작업·스케줄링은 완전히 격리하지 못했으며 표본은 작다.
첫 단위의 CLI 개선율과 이번 observer 개선율을 더해 종합 속도 개선율로 안내하지 않는다.
Go cold/warm 컴파일·HTTP 실행·TypeScript·전체 Graph·Cloudflare·다른 플랫폼의
성능은 이번에 새로 검증하지 않았다. 공개 문서에 로컬 수치를 게시하지 않는다.
