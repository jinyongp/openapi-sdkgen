# 선택 방식별 비용 비교

생성할 API를 줄이면 소스와 검사 비용을 줄일 수 있습니다. 애플리케이션에서 어떤
진입점을 가져오는지는 초기 로딩과 배포 파일의 크기를 결정합니다. 두 비용은
구분해서 봐야 합니다. 전체 SDK에서도 작은 번들이 나올 수 있고, 처음 가져오는
코드가 작아도 배포해야 하는 파일은 많을 수 있습니다.

## 작은 API의 실행 코드 비용 {#small-api-runtime}

현재 개발 버전은 생성 대상 API에 필요한 실행 코드를 자동으로 선택합니다.
아래 표본은 Bearer 인증, 객체·배열 검증, 문자열 길이와 객체 속성 제약을 사용하는
JSON API 세 개입니다.
네 번들 모두 같은 `getItem` 요청을 보내며 모의 Fetch로 URL, 인증 정보, 반환 DTO를
확인합니다. 기본 진입점에는 별도의 선택 설정을 지정하지 않았습니다.

| 생성 방식 | 전체 TypeScript 파일 | 전체 소스 행 | 실행 코드 파일 | 실행 코드 행 |
| --- | ---: | ---: | ---: | ---: |
| 기본 생성 | 94 | 7,754 | 49 | 5,623 |
| 전체 기능 시험 대조군 | 180 | 16,275 | 142 | 14,467 |

| 애플리케이션 진입점 | JS 청크 | 진입점 JS 바이트 | 진입점 gzip 바이트 | 전체 배포 JS 바이트 | 전체 배포 gzip 바이트 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 전체 기능 시험 대조군 | 1 | 106,930 | 30,805 | 106,930 | 30,805 |
| 기본 루트 | 1 | 31,904 | 9,603 | 31,904 | 9,603 |
| 정적 선택형 | 3 | 22,224 | 7,343 | 39,326 | 13,806 |
| 지연 선택형 | 7 | 369 | 274 | 40,536 | 15,029 |

이 표본의 기본 루트는 **JS 31.16 KiB, gzip 9.38 KiB**로, 대조군의 압축 크기에서
약 3분의 1 수준으로 줄었습니다. 정적·지연 준비 방식은 진입점을 줄이지만 이 작은 API에서는
전체 배포 압축 용량이 루트보다 큽니다. 처음 읽는 용량만으로 호출을 완료하는 데
필요한 비용을 판단할 수는 없습니다. 요청 처리, 검증, 오류 처리, 클라이언트 API의
공통 비용은 필요한 기능만 생성해도 남습니다.

전체 기능 대조군은 현재와 같은 실행 구현에 시험 준비 단계에서 모든 기능을 연결한
SDK입니다. 동작이 다른 과거 릴리스 대신 같은 소스에서 기능 선택의 효과를
비교했습니다. 앞서 보고된 esbuild 기준 약 97 KB / gzip 28.8 KB는 입력과 도구
설정이 달라 이 표의 기준값으로 사용하지 않았습니다.

저장소를 내려받고 TypeScript 검증 의존성을 설치한 뒤 재현할 수 있습니다.

```sh
devtools run runtime-features:perf
```

이 명령은 선택적으로 실행하는 측정입니다. 클라이언트·서버 예제 73개를 실제로
생성하고, 시나리오 226개를 같은 소스의 대조군과 비교합니다. 모듈 제외 조건
3,290개도 대조군에는 해당 모듈이 포함되는지 확인한 뒤 네 브라우저 번들을 측정합니다.
별도 회귀 검사에서는 TypeScript 5.7.3·5.9.3·6.0.3·7.0.2로 엄격한 생성 소스 검사와
원본 소스 없이 선언 파일만 가져오는 소비자 검사를 실행합니다. 일반 CI는 동작과
의존성을 검사하며 바이트·행 수의 고정 기준을 두지 않습니다.

2026년 10월 4일 한국시간 기준으로 측정했습니다. 커밋 `6c349f9`에서 작업 중인
미커밋 개발 버전이며 생성기 소스 해시는 `4c47c6012ef5`로 시작합니다.
<a :href="withBase('/benchmarks/runtime-features-results.json')">원본 결과</a>에 생성기·입력·생성 소스의 해시와

Vite 8.3.0 / Rolldown 1.2.6, 브라우저 ESM, ES2022, Oxc 최소화, 청크 분할,

모든 API의 크기를 보장하는 수치가 아니라 재현 가능한 표본입니다.

## API를 1개, 2개, 3개 쓸 때

스키마 프로그램을 도입하기 직전의 작업 트리를 보관한 뒤, 같은 입력과 도구
조건으로 현재 생성기와 비교했습니다. CLI의 `--operation`으로 API를 선택하고,
기본 루트를 쓰는 번들에서 선택한 API를 모두 호출합니다. 쿼리 표본에는 필수 정수
쿼리 하나를 추가했습니다. 아래 용량은 바이트 단위입니다.

| 선택한 API | 이전 JS | 현재 JS | 이전 gzip | 현재 gzip | 현재 TS 파일 / 행 | 현재 실행 코드 파일 / 행 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 조회 1개 | 31,082 | 29,569 | 10,160 | 9,283 | 80 / 7,043 | 48 / 5,655 |
| 쿼리 있는 조회 1개 | 34,536 | 32,890 | 11,072 | 10,174 | 82 / 7,348 | 49 / 5,912 |
| 조회·목록 2개 | 31,574 | 31,015 | 10,228 | 9,494 | 86 / 7,414 | 48 / 5,655 |
| 조회·생성 2개 | 32,011 | 30,575 | 10,289 | 9,430 | 86 / 7,406 | 49 / 5,672 |
| 조회·목록·생성 3개 | 32,495 | 32,013 | 10,358 | 9,633 | 92 / 7,772 | 49 / 5,672 |

다섯 번들 모두 JS와 gzip이 줄었습니다. 책임별로 모듈을 나누면서 파일 수는
늘었으므로 파일 개수만으로 배포 용량을 판단하면 안 됩니다. 생성기는 계약에 맞는
검증·변환 프로그램을 만들고 실행 의미가 같은 프로그램을 공유합니다. 일반 JSON은
필요한 실행 연산만 가져오며 범용 스키마 해석기를 포함하지 않습니다. 임의 스키마를
받는 공개 도우미 함수를 명시적으로 가져오면 기존의 전체 호환 구현을 사용합니다.

API 세 개 행은 세 개를 모두 호출합니다. 앞의 기본 루트 표는 `getItem`만 호출하므로
번들 크기가 다릅니다. 표본의 생성 옵션 차이로 소스 수치도 달라질 수 있습니다.
<a :href="withBase('/benchmarks/schema-operation-results.json')">변경 전후 원본 측정</a>에는 각 행의
엄격한 소스 컴파일과 모의 Fetch를 사용하는 실제 번들 호출 결과를 기록했습니다.
이 표본만으로 모든 SDK의 최소 크기를 보장하지는 않습니다.

## 현재 API 1,000개의 스키마 프로그램 비교

같은 변경 전 소스를 기준으로 비교했습니다. 현재 생성기는 전체 API 1,000개에서
스키마 프로그램 6개를 공유합니다. 공개 API 10개와 비공개 Link 대상을 선택하면
프로그램 4개를 생성합니다. 이름 있는 클라이언트와 일반 선택은 프로그램 파일과 내용이
완전히 같습니다.

아래 수치는 이전 → 현재입니다. 브라우저 번들은 각각 `getItem0`를 실제 호출하며,
루트 진입점에는 생성 범위의 API가 남습니다.

비용은 추가됐습니다. 프로그램 공유로 API마다 코드를 복제하지 않아도 전체 SDK가

생성은 빈 출력 디렉터리와 새 프로세스로 세 번 실행했습니다. 엄격 소스 검사와
선언 출력은 각각 새 컴파일러 프로세스로 한 번 실행했으며 생성 코드의
`@ts-nocheck`를 제거했습니다. 파일 캐시가 예열된 상태에서 순차 실행한 관측값이므로
시간 차이를 안정적인 속도 개선으로 해석하면 안 됩니다. 원본에는 이전 버전의 시간,

결과가 있습니다. 컴파일러 버전과 번들 조건은 앞의 작은 표본과 같습니다. 아래에
설명한 이전의 API 1만 개 타입 추론 한계를 해결한 결과는 아닙니다.

## 생성 소스와 자원 사용

전체 SDK는 모든 API를 생성합니다. 일반 selection은 선택한 10개와 Link 의존성만
생성합니다. named selection은 같은 API를 이름 있는 클라이언트 하나에 배정하고,
루트에서 그 합집합을 제공합니다. `selection + named`는 같은 루트 선택을 명시해
기본 합집합과 결과가 같은지도 확인하는 설정입니다.

<SelectionBenchmarks locale="ko" group="generation" />

이 표본에서 일반·named selection은 약 3초 걸리던 생성을 0.1초 미만으로 줄였습니다.
named 설정은 진입점·타입 파일 네 개와 14,105바이트를 추가하지만 API 구현은
공유합니다. 루트 선택을 생략한 결과와 같은 선택을 명시한 결과는 파일별 바이트까지
같습니다.

API 전부를 선택한 결과는 전체 생성의 6,060개 파일과 크기가 같습니다. 측정에는
기본 생성 옵션을 사용했습니다. 선택 기록은 `--with metadata`를 켰을 때만
추가합니다. 전체 API를 선택한다고 생성이 빨라지지는 않습니다. 입력 로딩과 문서
검증은 선택 여부와 관계없이 전체 원문을 대상으로 합니다.

## 애플리케이션 번들

루트와 named 진입점은 같은 10개 API를 제공합니다. 정적 loader는 operation 참조를
직접 import한 뒤 `loadOperations`에 전달합니다. 동적 lookup은 `routes[route]`를
사용하며, 생성 범위의 operation ID·경로 lookup 파일을 모두 배포합니다. 어느 방식이든
Link 대상은 후속 호출에 사용할 수 있지만 공개 메서드로는 제공하지 않습니다.

<SelectionBenchmarks locale="ko" group="bundle" />

이 표본에서는 named 진입점의 배포 번들이 가장 작고 loader보다 준비도 빠릅니다.
일반 루트 진입점은 준비가 빠르지만 정적 loader보다 배포 JS가 큽니다. 전체 SDK와
selection SDK에 정적 `loadOperations`를 사용한 결과는 배포 용량 차이가 35바이트뿐입니다.
정적 import에서 번들러가 불필요한 API를 이미 제거하기 때문입니다. 이 경우에도
selection은 생성과 소스 검사 비용을 줄이는 데 도움이 됩니다.

동적 lookup의 최초 import는 약 6.2 KiB입니다. API를 준비할 때 추가 모듈을 읽습니다.
전체 lookup을 배포하면 임의 API 선택을 지원할 JS 파일 3,004개가 필요하고, 선택한
범위만 생성하면 34개입니다. 선택한 10개를 준비한다고 모든 파일을 읽는 것은
아닙니다. 배포 자산을 줄이는 효과와 한 번의 방문에서 읽는 코드를 줄이는 효과는
다릅니다. 작은 파일을 여러 개 읽으면 요청 수와 파일별 압축 비용도 고려해야 합니다.

## 수치 읽는 방법

크기 그래프는 모두 0에서 시작하는 선형 축입니다. 지표를 바꾸면 축도 다시 계산하므로
같은 그래프 안의 막대를 비교하세요. 시간 막대는 중앙값, 선은 최소–최대 범위입니다.
수치 표도 함께 제공해 색이나 마우스 조작 없이 결과를 확인할 수 있습니다.
작은 화면에서는 그래프를 가로로 스크롤할 수 있습니다.

‘준비까지 읽은 JS’는 첫 API 요청 전까지 진입점을 가져오고 10개 API를 준비하는 데
읽은 코드입니다. ‘전체 배포 JS’는 사용하지 않은 lookup 파일과 지연 청크까지
포함합니다. 원본 측정에는 최초 import와 비공개 Link 호출 뒤의 로딩도 기록했습니다.
Gzip 수준 6과 Brotli 품질 5로 각 파일을 따로 압축한 크기를 합산했습니다.
디스크 할당량, 소스맵, HTML, HTTP 헤더, 문서 사이트의 차트 코드는 SDK 번들에
포함하지 않았습니다.

생성은 방식마다 새 프로세스와 비어 있는 출력 디렉터리로 세 번 측정했습니다.
번들 빌드는 세 번, 실행은 새 프로세스에서 여섯 번씩 순서를 바꿔 측정했으며 파일
캐시는 예열된 상태였습니다. Rolldown 1.2.6으로 브라우저용 ESM을 최소화하고
불필요한 코드를 제거했으며 청크 분할을 켰습니다. 동적 lookup 모듈도 빌드 입력에
넣어 경로를 유지했습니다. 최소화하지 않은 JS를 배포 폴더에 복사하지 않았습니다.
실제 HTTP 대신 모의 Fetch로 요청과 응답을 확인했습니다.

실행 시간은 Node.js 24.21.0에서 측정했습니다. 브라우저 네트워크, 서비스 워커,
브라우저 캐시, 실제 서버 응답 시간은 측정하지 않았습니다. 환경은 AMD Ryzen 7
9800X3D, 약 15.2 GiB 메모리, WSL2의 Linux x64입니다. 생성에는 Go 1.27.1,
JS 출력에는 TypeScript 7.0.2를 사용했습니다. 시간 측정용 생성 코드의 기본
`@ts-nocheck`는 유지했습니다. 별도의 회귀 검사에서는 이를 제거하고 TypeScript
6.0.3·7.0.2의 엄격 타입 검사와 실행 동작을 확인했습니다.

## 검증 범위와 남은 한계

선택이 겹쳐도 공통 구현이 중복되지 않는지, 루트와 named의 공개 타입이 독립적인지,
비공개 API의 직접 준비를 거절하는지, 연쇄 Link 실행이 유지되는지 확인했습니다.
metadata 옵션과 동일 선택의 파일 일치도 검사했습니다. 전체 Go 검사, TypeScript
6·7의 엄격 타입·실행 회귀, 문서 검사, 서식 검사, Go vet가 통과했습니다. 앞선 런타임
검사는 732개가 통과했고 선택 실행하는 성능 검사 7개는 건너뛰었습니다. Graph 타입
검사는 이번 범위에서 제외했습니다.

이 결과가 더 최적화할 곳이 없다는 뜻은 아닙니다. 일반 루트 진입점의 추가 번들 비용과
동적 lookup의 배포 용량·파일 수는 후속 분석 대상입니다. 여러 페이지를 각각 빌드할
때의 전체 비용, 브라우저 다운로드, 다양한 선택 비율은 이번 표본으로 판단할 수 없습니다.

앞선 1만 API 전체 SDK 표본에서는 명시적인 `Client<Chosen>` 변수와 `createClient`
호출 타입 추론을 함께 사용한 소비자에서 TypeScript 추론 복잡도 오류가 발생했습니다.
그 실험에서 `createClient<Chosen>` 타입 인자를 명시하면 TypeScript 6·7 모두
통과했습니다. 이번 1,000개 벤치마크는 그 큰 타입 추론 경로를 수정하거나 다시
검사한 결과가 아닙니다. 일부 타입 회귀 검사의 통과를 모든 대규모 소비자의 통과로
해석하면 안 됩니다.

named 설정만으로 전체 루트를 만들던 과거 측정은 현재 그래프에 사용하지 않습니다.
공개 파일에서 로컬 사용자 경로는 제거했습니다.

로컬 Go·Node 환경과 검증 의존성을 준비한 저장소에서 실행합니다.

```sh
devtools run build:dev
devtools run selection:perf
```

결과는 `.tmp/selection-benchmark/report.json`에 저장합니다. 저장소의 표본과 실행
검사를 사용하며, 측정 중에는 다른 빌드나 검사를 함께 실행하지 마세요.
이 성능 측정은 선택 실행하는 명령입니다. CI에 시간 임계값을 추가하지 않습니다.
